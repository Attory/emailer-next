# Emailer Next 0.9.0 installation walkthrough findings

**Status:** Phase 13 acceptance repair record from the first hands-on `0.9.0`
server installation. This is a redacted product-development reference, not a
client incident log or a substitute for the installation manual.

No database password, MariaDB administrator credential, Owner password, TOTP
seed, provisioning URI, recovery code, session identifier, private key, or
private filesystem output has been copied into this record. Hostnames and
addresses in examples are synthetic.

## How to use this record

- `CLIENT-INSTALL-0.9.0.md` remains the runnable acceptance manual.
- `CLIENT-INSTALL-1.0.0.md` remains the production-oriented Version-1 manual.
- This record preserves every question, failure, answer, and resulting repair
  from the first acceptance walkthrough so later candidates do not repeat it.
- During iterative acceptance, a changed loose installer or manual may be
  copied by itself. Rebuild the signed application ZIP only when its packaged
  application content changes. Refresh final hashes and candidate evidence at
  the client-delivery boundary.

## Packaging and delivery questions

### Where is `emailer-next-0.9.0.zip`?

It is inside the generated `emailer-next-0.9.0-candidate/` directory. The
candidate builder prints its full path. The manual now shows the complete
directory layout and transfer commands rather than referring to an archive
that the operator has not yet received.

### What are the four sidecars, and why are they needed?

The four files alongside the ZIP are:

1. `.manifest.json` — the bounded package contract and file inventory;
2. `.sha256` — the archive digest;
3. `.spdx.json` — the software bill of materials;
4. `.sig` — the detached release signature.

The root installer consumes them automatically before extraction. A client
does not edit, open, or pass them as command-line options; the complete
candidate directory must simply remain together.

### Why was an install manual delivered before the distributive existed?

That ordering was unsuitable for human acceptance. The acceptance workflow now
produces the runnable `0.9.0` directory first and bundles its short manual and
accessibility checklist with it. Human accessibility acceptance is performed
against that installed candidate, not against documentation alone.

### Does every installer edit require rebuilding the ZIP?

No. The root installer is a loose file beside the signed application ZIP. A
development-only installer edit can be copied by itself. The final candidate
record and hashes are refreshed only for a delivery checkpoint; the application
ZIP is rebuilt only when packaged application content changes.

### How is the candidate copied over SSH?

Copy the complete directory with `scp -r` or `rsync -a`, then run the installer
from inside that directory as root. The manual includes exact synthetic
examples and a server-side file-list check.

## Root installer questions and failures

### Why did the installer not install PHP, MariaDB, Nginx, or Mailpit itself?

The acceptance installer now checks and provisions all required packages. On
supported Debian/Ubuntu systems it adds the appropriate PHP and MariaDB
repositories when the distribution repositories do not provide PHP 8.4/8.5 or
MariaDB 10.11/11.8. Mailpit is downloaded at a pinned version and verified by a
pinned digest. The final production description must disclose these installed
packages and repositories.

### Why did package installation ask how to handle `50-server.cnf`?

The installer now uses noninteractive APT, retains locally modified
configuration by default, suppresses package-change prompts, and permits
`needrestart` to handle required service restarts automatically. Lines beginning
with `NEEDRESTART-SVC` are informational package-maintenance output, not an
Emailer Next failure.

### What does `HTTPS hostname` mean?

Enter only a hostname such as `mailer.example.com`, without `https://`, a port,
or `/setup`. The installer now explains this before prompting.

### Why could a remote browser not find the server?

The installer cannot create a DNS record. Before remote access, the hostname's
DNS A/AAAA record must point to the server. The installer and manual now say so
before the browser step. DNS propagation is an external prerequisite, not an
application repair.

### Why did `/setup` return Not Found while a loopback request returned 200?

An existing Apache service owned ports 80/443 while the first installer only
configured Nginx. The acceptance installer now detects an active supported web
server, configures either Apache or Nginx with the exact `public/` document root
and PHP-FPM socket, and adds an HTTP-to-HTTPS redirect. It no longer reports
Nginx success when Apache is actually serving the hostname.

### Why did Apache warn that the self-signed certificate was a CA certificate?

The first OpenSSL invocation did not explicitly mark the disposable certificate
as an end-entity server certificate. It now sets `CA:FALSE`, server-auth
extended usage, and bounded key usage. The generated certificate remains
acceptance-only and must never be used for public operation; production
requires a properly issued hostname certificate.

### Why did local MariaDB administration fail?

MariaDB `root` may use socket authentication, a distribution maintenance
account, a hosting-panel-managed password, or another existing policy. The
installer first tries safe socket and distribution-maintenance access, then
asks for an existing administrator account. This password is used only to
create the restricted application database/user and is not the later
application database or Owner password.

### Why did the supplied MariaDB root password fail?

The typed value was not accepted by the server's configured authentication
policy. The correct diagnostic is an administrator login test, not repeated
guessing. Existing hosting-panel configuration may use a different credential.
The installer supports supplying an already-created restricted application
`DATABASE_URL` when local administration is intentionally unavailable.

### What did the `mysql.column_stats` errors mean?

They showed MariaDB system tables from an older server version after a package
upgrade. They were distinct from the Emailer Next empty application database.
The installer now preserves an already supported MariaDB installation instead
of upgrading it, and runs `mariadb-upgrade` through the same authenticated
administrator channel when an unsupported installation had to be upgraded.
Application credentials are never used to repair system tables.

### Why was `verify-package.php` reported missing even though it was supplied?

The verifier was under a root-only staging directory and therefore unreadable
by the least-privilege `emailer` verification process. The installer now stages
the archive, all four sidecars, verifier, and inspector in a temporary readable
verification directory, verifies as `emailer`, and removes that staging area.

## Browser setup questions and failures

### Why was a setup challenge already active?

Only one 15-minute ownership challenge can exist. Its code is shown once in the
original browser session and cannot be redisplayed. The UI now distinguishes
the original-session retry from waiting for expiry and starting a new session.

### Why did setup appear to require HTTP?

Secret-bearing setup steps require HTTPS. HTTP may show only the initial proof
instruction and should redirect to HTTPS after web-server configuration. A
certificate must be trusted or deliberately accepted for a disposable
self-signed test. Production must use a valid hostname certificate.

### Why was the ownership proof rejected after the helper reported success?

The first helper placed a root-owned proof inside an immutable root-owned
release directory. PHP-FPM could neither read nor delete it. The installer now
uses an externally configured service-owned setup directory, writes a mode
`0600` proof owned by `emailer`, and leaves the release tree immutable. The UI
also says to use the same browser session and the supplied helper.

### Where does the browser database password come from?

When the installer creates the local database, it prints one generated
**application database password** with the host, port, database, and username.
It is not the MariaDB administrator/root password and not the Owner password.
The browser page now states this explicitly. The same protected connection is
stored in `/etc/emailer/runtime.env`; secret values are not stored in setup
state or redisplayed by the browser.

### Why did database or installation-key setup fail with one generic message?

Database/schema failure and external-master-key failure were combined. They now
produce separate safe messages: one directs the operator to the restricted
application credentials; the other directs the operator to key-directory
ownership and mode checks. Neither message exposes a credential or private
path.

### What should be rerun after manual migrations succeed?

Return to the browser database form and submit the same restricted application
credentials again. The migration is idempotent; the step then validates the
schema and initializes the external master key. The preferred repaired path is
for the browser step to perform this itself, without a manual migration.

### What is the canonical HTTPS base URL?

It is the public HTTPS origin only, for example
`https://mailer.example.com`. Do not append `/setup`, `/admin`, a query, or a
fragment. It must match the hostname configured in the runtime. The
organisation page now provides this definition and example.

### Where does the current six-digit TOTP code come from?

Add the displayed provisioning URI or TOTP seed to an authenticator app. That
app generates a six-digit code every 30 seconds. Recovery codes are stored
separately and used only when the authenticator is unavailable. The enrolment
page now gives these steps before asking for a code.

### What should be entered for Mail transport and sender identity?

For acceptance setup, use the root-installed loopback Mailpit service at
`127.0.0.1:1025`. The sender is a synthetic/test identity. This proves local
mail generation only; configure authenticated, peer-verified production SMTP
under **Mail** after setup and before public delivery. The page no longer
defaults a bare-metal installation to the unresolved hostname `mailpit`.

### What do delivery limits and privacy defaults do?

They record safe ceilings and defaults; they do not send a campaign. The UI now
briefly explains pacing, concurrency, retries, retention, supervised services,
and that tracking/RSVP stay disabled.

### What does final critical preflight do?

It validates the completed setup state and permanently publishes the install
lock. It sends no campaign. After success, `/setup` returning Not Found is
intentional; continue at `/login`. The button and supporting text now state
this consequence directly.

## Dashboard, Doctor, and backup questions

### Why did the dashboard report that no Owner/key/origin/sender existed after setup?

The operations timer had recorded a full Doctor run before setup completed,
while login performed only a cached lightweight run that did not retire old
full-run findings. Scheduled operations now treat any Doctor evidence older
than installation completion as immediately due, and the Doctor page explains
that **Run full Doctor now** refreshes persisted evidence and clears resolved
findings.

### Which fresh-install findings are expected?

A new installation has no recent verified backup, external backup transfer, or
recovery-key package. Local Mailpit is also not production authenticated TLS
SMTP. These are real go-live prerequisites, but they do not mean that the
Owner, database, or setup lock is missing. UI guidance distinguishes the local
on-demand backup from optional external automation.

### What do the backup policy fields mean?

The filesystem destination is an operator-provisioned mount outside release and
private application storage. The browser stores only the adapter and schedule,
never the path. Run interval controls automated creation, retention bounds
eligible automated history, and restore-drill target records the maximum
planned interval—it never performs an unattended restore. For acceptance, keep
the destination disabled and create a local on-demand backup.

### Why did Create and verify backup return an unexplained 403?

Backup actions require purpose-bound recent Owner re-authentication. The page
omitted the link, used ambiguous “fresh password” wording, redirected away from
the task, and allowed a failed assertion to become a generic 403. Repairs now:

- link directly from Backups to confirmation for `backup_management`;
- say **current account password**, not “fresh password”;
- explain the current authenticator/recovery-code field and five-minute,
  same-browser-session scope;
- redirect successful confirmation back to Backups; and
- redirect an expired/missing assertion to confirmation with a useful message
  instead of showing the generic error page.

The protected CLI `emailer:backup:create` remains the non-HTTP operational
alternative and creates plus verifies the encrypted local backup.
